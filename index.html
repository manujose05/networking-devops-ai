What is it?

The OSI (Open Systems Interconnection) model breaks down how computers communicate into 7 layers. Think of it like sending a physical letter — you write the content, put it in an envelope, write the address, hand it to a postman, it goes on a truck, then a plane, arrives at a local post office, and finally gets delivered. Each step is a "layer."

Every time you visit a website, your data travels down all 7 layers on your computer, across the network, and back up all 7 layers on the server.

The 7 Layers (memorize this table)

#NameWhat it doesReal exampleYou care about?
7ApplicationWhat apps use to communicateHTTP, DNS, FTP, SMTPYES
6PresentationEncryption & data formattingTLS/SSL, JPEG, MP4Sometimes
5SessionManages open connectionsLogin sessions, NetBIOSSometimes
4TransportReliable delivery, portsTCP, UDPYES
3NetworkRouting between networksIP addresses, routersYES
2Data LinkLocal delivery on same networkMAC addresses, switchesLess often
1PhysicalActual hardware & signalsEthernet cable, WiFi radioLess often
As a DevOps/cloud engineer, you'll mostly work with Layer 3 (IP), Layer 4 (TCP/UDP/ports), and Layer 7 (HTTP, DNS). Focus there first.

Memory trick

To remember the layers from 7 down to 1: "All People Seem To Need Data Processing"

Application → Presentation → Session → Transport → Network → Data Link → Physical

Real-world example: You type google.com

Layer 7 — Your browser creates an HTTP request: "GET / HTTP/1.1"
↓
Layer 6 — TLS encrypts the data (HTTPS)
↓
Layer 4 — TCP adds port numbers (your port → port 443)
↓
Layer 3 — IP adds source + destination IP addresses
↓
Layer 2 — MAC address added for local network hop
↓
Layer 1 — Electrical signals sent over the cable or WiFi

Practice exercise

  1. Open your browser and visit any website over HTTPS.
  2. Right-click → Inspect → Network tab.
  3. Click on any request. You can see Layer 7 (HTTP headers), Layer 4 (protocol: TCP), and Layer 3 (Remote Address = IP).
  4. Try to identify what layer each piece of information belongs to.

What is an IP address?

An IP address is like a postal address for your computer. Without it, data packets wouldn't know where to go. Every device on a network — your laptop, phone, a server in AWS — has an IP address.

There are two versions:

  • IPv4: 192.168.1.100 — 4 groups of numbers (0–255), written with dots. Only ~4 billion possible addresses. We're running out.
  • IPv6: 2001:0db8:85a3::8a2e:0370:7334 — 8 groups of hex digits. 340 undecillion addresses. Practically unlimited.

Private vs Public IP

TypeRangeWhere usedExample
Private10.0.0.0/8Large corporate networks10.0.0.5
Private172.16.0.0/12Medium networks172.16.5.3
Private192.168.0.0/16Home / small office192.168.1.100
PublicEverything elseThe internet8.8.8.8
Your home router has ONE public IP (given by your ISP). Every device in your house gets a private IP. The router translates between them — this is called NAT (Network Address Translation).

Subnets and CIDR notation

A subnet divides a large network into smaller, manageable chunks. The CIDR notation (the /number) tells you how many bits are the "network" part vs the "host" part.

192.168.1.0/24 means:

  • First 24 bits = network address (192.168.1)
  • Last 8 bits = host addresses (.0 to .255)
  • That's 256 total addresses, 254 usable (first and last reserved)
CIDRUsable hostsCommon use
/321Single host (firewall rules)
/24254Small office, cloud subnet
/1665,534Large VPC in cloud
/816,777,214Enterprise networks

Linux commands to check IPs

# See your machine's IP addresses
ip addr show

# Short version — just IPs
ip addr show | grep "inet "

# Older command (still works)
ifconfig

# Check your public IP (uses an external service)
curl ifconfig.me

Practice exercise

  1. Open a terminal on your Linux machine and run ip addr show.
  2. Find your private IP — it likely starts with 192.168 or 10.
  3. Run curl ifconfig.me — this is your public IP (your router's IP).
  4. Notice they are different. That difference is NAT in action.

What is DNS?

Computers communicate using IP addresses like 142.250.80.46. But humans remember names like google.com. DNS is the system that translates between them — it's essentially the phonebook of the internet.

When you type google.com in your browser:

1. Your browser checks its local cache — "Do I already know this IP?"
↓
2. Asks your OS (which checks /etc/hosts on Linux)
↓
3. Asks your configured DNS server (e.g. 8.8.8.8 = Google DNS)
↓
4. DNS server responds: "google.com = 142.250.80.46"
↓
5. Browser connects to 142.250.80.46 on port 443

DNS Record Types

RecordWhat it doesExample
ADomain → IPv4 addressgoogle.com → 142.250.80.46
AAAADomain → IPv6 addressgoogle.com → 2607:f8b0::200e
CNAMEAlias — one domain to anotherwww.google.com → google.com
MXMail server for a domaingoogle.com → smtp.google.com
TXTText data (verification, SPF)Used by Google/AWS to verify ownership
NSName servers for a domainPoints to the DNS authority

Linux DNS commands

# Look up any domain
dig google.com

# Get just the A record (IP)
dig google.com A +short

# Look up mail records
dig google.com MX

# Reverse lookup — IP to domain
dig -x 8.8.8.8

# Simpler DNS lookup tool
nslookup google.com

# Which DNS server is your machine using?
cat /etc/resolv.conf

# The hosts file — manual overrides (checked BEFORE DNS)
cat /etc/hosts
In DevOps you'll use DNS constantly — to point your domain to a load balancer, to set up mail, to verify SSL certificates. Learn dig well.

DNS in cloud (AWS Route 53 example)

When you deploy an app to the cloud:

  • Your app runs on a server with IP 54.100.200.50
  • You create an A record in Route 53: myapp.com → 54.100.200.50
  • Users type myapp.com, DNS resolves it to your server IP
  • When you scale to 3 servers, you put a load balancer in front and point DNS to the LB instead

Practice exercise

  1. Run dig google.com — find the IP address in the ANSWER SECTION.
  2. Run dig google.com MX — find Google's mail servers.
  3. Run dig github.com +short — get just the IP, no clutter.
  4. Open /etc/hosts — you'll see 127.0.0.1 localhost. This is why typing "localhost" works.

TCP — Transmission Control Protocol

TCP is like sending a registered letter with a tracking number. The receiver must sign for it. If it gets lost, it's re-sent. This makes it reliable but slower.

TCP does a "3-way handshake" before sending any data:

Your computer → Server: "SYN" (I want to connect)
↓
Server → Your computer: "SYN-ACK" (OK, I'm ready)
↓
Your computer → Server: "ACK" (Great, let's go)
↓
Data flows — every packet acknowledged

Used for: web browsing (HTTP/HTTPS), file transfers, SSH, email — anything where you can't afford to lose data.

UDP — User Datagram Protocol

UDP is like shouting across a room. You send the message and don't wait for confirmation. It's fast but unreliable — some packets may be lost.

Used for: video streaming, online gaming, DNS lookups, VoIP calls — where speed matters more than perfection (a dropped frame in a video is fine; waiting for it to re-send is not).

TCPUDP
ReliabilityGuaranteed deliveryBest-effort, may drop
SpeedSlower (handshake + ACKs)Faster (fire and forget)
OrderPackets arrive in orderMay arrive out of order
Use caseSSH, HTTP, databasesVideo, DNS, gaming

Ports — knocking on the right door

An IP address gets data to the right machine. A port number gets it to the right application on that machine. Think of the IP as a building address and the port as the apartment number.

PortProtocolWhat it's for
22TCPSSH — remote login to a Linux server
80TCPHTTP — unencrypted web traffic
443TCPHTTPS — encrypted web traffic
53UDPDNS — name resolution
3306TCPMySQL database
5432TCPPostgreSQL database
6379TCPRedis cache
8080TCPCommon dev/test HTTP port
Ports 0–1023 are "well-known" and reserved for system services. Ports 1024–65535 are for apps. Databases should NEVER be open on port 3306/5432 to the public internet.

Linux commands to inspect ports

# See all listening ports on your machine
ss -tulpn

# What's using port 80?
ss -tulpn | grep :80

# Check if a remote port is open
nc -zv google.com 443

# Or with telnet
telnet google.com 443

# See all active connections
ss -tn

Practice exercise

  1. Run ss -tulpn on your Linux machine. See which ports are listening.
  2. If you have a web server running, you should see port 80 or 443 in the list.
  3. Run nc -zv google.com 443 — if it says "Connected", port 443 is open on Google's server.
  4. Try nc -zv google.com 22 — this should fail (Google doesn't allow SSH from the internet).

ip — the main networking tool

# Show all network interfaces and their IPs
ip addr show

# Show just a specific interface
ip addr show eth0

# Show routing table (how traffic leaves your machine)
ip route show

# Add a static route
ip route add 10.0.0.0/24 via 192.168.1.1

# Show neighbours (like ARP table — maps IPs to MACs)
ip neigh show

ping — is the host alive?

# Basic ping
ping google.com

# Ping only 4 times (instead of forever)
ping -c 4 google.com

# Ping with a specific packet size (useful for MTU testing)
ping -s 1400 google.com

# Ping a specific IP
ping 8.8.8.8

If ping fails it could mean: host is down, firewall is blocking ICMP, or DNS can't resolve the name. Try pinging the IP directly to rule out DNS issues.

traceroute — follow the path

# Show every router hop between you and the destination
traceroute google.com

# Use TCP instead of ICMP (bypasses some firewalls)
traceroute -T google.com

# Use UDP
traceroute -U google.com

Each line is one "hop" — a router your packet passed through. The number is the latency in ms. A * means the router didn't respond (firewall). Great for diagnosing where packets get lost.

ss and netstat — port and connection inspection

# All listening TCP/UDP ports
ss -tulpn

# -t = TCP, -u = UDP, -l = listening, -p = process name, -n = numeric (no DNS lookup)

# All established connections
ss -tn

# All connections to a specific port
ss -tn dst :443

# Older equivalent
netstat -tulpn

curl — test HTTP from terminal

# Fetch a webpage
curl https://google.com

# See the HTTP headers (useful for debugging)
curl -I https://google.com

# Send a POST request (like an API call)
curl -X POST https://api.example.com/data \
  -H "Content-Type: application/json" \
  -d '{"key": "value"}'

# Follow redirects (-L) and be verbose (-v)
curl -Lv https://google.com

# Download a file
curl -O https://example.com/file.zip
curl is your best friend for testing APIs, checking if a server responds, and debugging HTTP issues. Learn it well.

ufw / iptables — firewall

# Check firewall status
ufw status

# Enable firewall
ufw enable

# Allow SSH (always do this before enabling the firewall!)
ufw allow 22/tcp

# Allow HTTP and HTTPS
ufw allow 80/tcp
ufw allow 443/tcp

# Block a specific IP
ufw deny from 192.168.1.100

# Delete a rule
ufw delete allow 80/tcp

Practice exercise — full networking workout

  1. Run ip addr show — write down your private IP.
  2. Run ip route show — find your default gateway (the router's IP).
  3. Run ping -c 3 8.8.8.8 — confirm you have internet access.
  4. Run traceroute google.com — count how many hops it takes.
  5. Run curl -I https://github.com — look at the HTTP status code (should be 200).
  6. Run ss -tulpn — identify every service listening on your machine.

What is DevOps?

Before DevOps, developers wrote code and "threw it over the wall" to an operations team who deployed it. This was slow and caused many conflicts. DevOps combines both roles and automates the entire journey from code to production.

The goal: deploy software faster, more reliably, and repeatedly — with no manual steps.

The full pipeline

1. Code — Developer writes code, pushes to Git (GitHub/GitLab)
↓
2. CI (Continuous Integration) — Automated system runs tests. If tests fail, deploy is stopped. Tools: GitHub Actions, Jenkins, GitLab CI
↓
3. Build — Code is packaged into a Docker container image
↓
4. CD (Continuous Deployment) — Image is automatically deployed to staging, then production
↓
5. Infrastructure — Servers/cloud resources managed as code (Terraform, Ansible)
↓
6. Monitor — Metrics, logs, alerts watched 24/7 (Prometheus, Grafana, Datadog)

Key DevOps tools to know

CategoryToolWhat it does
Version ControlGit, GitHubTrack code changes, collaborate
CI/CDGitHub Actions, JenkinsAutomate build, test, deploy
ContainersDockerPackage apps + dependencies together
OrchestrationKubernetesRun and manage many containers
Infrastructure as CodeTerraformDefine cloud resources in code
Config ManagementAnsibleAutomate server configuration
MonitoringPrometheus + GrafanaMetrics collection and dashboards

Why load balancing?

If you have 1 server handling all traffic and it gets 10,000 requests/second, it crashes. A load balancer sits in front of multiple servers and distributes the traffic between them. If one server crashes, the LB stops sending traffic to it automatically — users don't notice.

                     ┌── Server 1 (handles ~33% of traffic)
Internet → Load ─────├── Server 2 (handles ~33% of traffic)
           Balancer  └── Server 3 (handles ~33% of traffic)

Load balancing algorithms

AlgorithmHow it worksBest for
Round RobinRotates through servers in order (1→2→3→1→2→3)Stateless apps where all servers are equal
Least ConnectionsSends to the server with fewest active connectionsLong-running connections (WebSockets)
IP HashSame client IP always goes to same serverApps that need "sticky sessions"
WeightedBigger servers get more traffic based on weightMixed server sizes

Layer 4 vs Layer 7 load balancing

  • Layer 4 (TCP/UDP) — Routes based on IP/port only. Fast but dumb. Doesn't understand HTTP. Example: AWS NLB.
  • Layer 7 (HTTP) — Understands URLs, headers, cookies. Can route /api/* to one set of servers and /images/* to another. Example: Nginx, AWS ALB, Cloudflare.
In cloud, you'll almost always use a Layer 7 (HTTP) load balancer like AWS ALB or Nginx. It lets you do smart routing, SSL termination, and health checks.

Nginx as a load balancer

# /etc/nginx/nginx.conf
upstream myapp {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}

server {
    listen 80;
    location / {
        proxy_pass http://myapp;
    }
}

What is a VPC?

A VPC (Virtual Private Cloud) is your own isolated network inside a cloud provider. It's like having your own private office building inside a massive shared data center. You control the IP ranges, subnets, routing, and firewall rules.

VPC architecture — the standard pattern

VPC: 10.0.0.0/16 (your whole network)
  │
  ├── Public Subnet: 10.0.1.0/24
  │     └── Load Balancer (has internet access)
  │
  └── Private Subnet: 10.0.2.0/24
        ├── App Servers (no direct internet)
        └── Database (no direct internet)
Golden rule: Databases must always be in a private subnet. Only load balancers should be in public subnets. App servers can go either way, but private is more secure.

Key VPC components

ComponentWhat it does
Internet GatewayConnects your VPC to the public internet
Route TableRules for where traffic goes (like a GPS for packets)
Security GroupVirtual firewall for EC2 instances — allow/deny by port and IP
NACLNetwork Access Control List — subnet-level firewall
NAT GatewayLets private subnet resources reach the internet (outbound only)
VPC PeeringConnect two VPCs so they can communicate privately

Security Groups vs NACLs

Security GroupNACL
Applies toIndividual EC2 instancesEntire subnet
StateStateful (return traffic auto-allowed)Stateless (must allow both directions)
DefaultDeny all in, allow all outAllow all in and out
Use forPer-server rulesSubnet-wide blocks

What is Docker?

Docker packages your application and all its dependencies into a single unit called a container. The container runs identically on your laptop, a CI server, or in production. No more "it works on my machine" problems.

  • Image: The blueprint (like a class in programming)
  • Container: A running instance of an image (like an object)
  • Dockerfile: Instructions to build an image
  • Registry: Where images are stored (Docker Hub, AWS ECR)

Docker networking modes

Network modeWhat it meansUse case
bridge (default)Container gets its own IP on a virtual networkMost apps
hostContainer shares the host machine's network stackHigh performance
noneNo network access at allIsolated processing
custom bridgeUser-defined network — containers find each other by nameMulti-container apps

Making containers talk to each other

# Create a shared network
docker network create app-network

# Start a database container on that network
docker run -d \
  --name postgres-db \
  --network app-network \
  -e POSTGRES_PASSWORD=secret \
  postgres:15

# Start your app on the same network
# It can reach the DB using hostname "postgres-db"
docker run -d \
  --name my-app \
  --network app-network \
  -p 8080:8080 \
  -e DB_HOST=postgres-db \
  my-app-image

# List networks
docker network ls

# Inspect a network — see which containers are on it
docker network inspect app-network
Containers on the same custom bridge network can reach each other by container name as a hostname. No IPs needed. DNS works automatically.

Port mapping — exposing containers

# -p HOST_PORT:CONTAINER_PORT
# Container listens on 8080 internally
# You access it on port 3000 from your machine
docker run -p 3000:8080 my-app

# Bind to a specific host IP
docker run -p 127.0.0.1:3000:8080 my-app

What is Kubernetes (K8s)?

Docker runs one container. Kubernetes runs hundreds or thousands of containers across many machines and manages them automatically — restarting crashed ones, scaling up when traffic increases, rolling out updates with zero downtime.

Key commands

# See all running pods and their IPs
kubectl get pods -o wide

# See all services
kubectl get services

# Expose a deployment as a LoadBalancer service
kubectl expose deployment myapp --port=80 --type=LoadBalancer

# See Ingress rules
kubectl get ingress

# Check pod logs
kubectl logs pod-name

# Get inside a running pod (like SSH for containers)
kubectl exec -it pod-name -- /bin/bash

How a request flows in Kubernetes

User → DNS resolves to Ingress IP
↓
Ingress routes /api/* to "api-service"
↓
Service load-balances across 3 Pods
↓
Pod handles the request, returns response

What to monitor

The RED method for services:

  • Rate — requests per second
  • Errors — error rate (%)
  • Duration — latency (how slow?)

The USE method for infrastructure:

  • Utilization — CPU/memory % used
  • Saturation — queue depth, wait time
  • Errors — disk errors, network drops

What is AIOps?

AIOps (Artificial Intelligence for IT Operations) uses machine learning to automate and enhance IT operations. Instead of a human watching dashboards at 3am, AI models continuously monitor your systems and detect, predict, and sometimes fix problems automatically.

Key AIOps capabilities

CapabilityWhat it doesReal example
Anomaly DetectionLearns "normal" — alerts when something unusual happensTraffic at 3am suddenly spikes 10x — alert fires
Predictive FailurePredicts hardware/software failure before it happens"Disk will fail in 48 hours" — replace it now
Root Cause AnalysisFinds the source of a problem across 100 microservices"Slowness caused by database query in user-service"
Auto-remediationAutomatically fixes known issuesMemory leak detected → pod restarted automatically
Noise ReductionFilters thousands of alerts down to the few that matterGroups 200 related alerts into 1 "incident"

How anomaly detection works

The AI model is trained on historical data — e.g., your CPU usage over the past 3 months. It learns patterns: traffic is high Mon–Fri 9am–6pm, low at night. Once trained:

  • Normal Saturday 2am CPU: 5% → no alert
  • Saturday 2am CPU suddenly hits 80% → anomaly detected → alert!

This catches attacks, runaway processes, or failures that static threshold alerts ("alert if CPU > 90%") would miss.

Tools

  • Datadog — Cloud monitoring with built-in anomaly detection. Free trial available.
  • Dynatrace — Fully automatic AI called "Davis" that does root cause analysis.
  • Splunk ITSI — AIOps for large enterprises.
  • New Relic — Applied Intelligence for alert grouping and correlation.

Why traditional security isn't enough

Traditional firewalls work with rules and known signatures — "block traffic from IP X" or "block files that match this virus signature". The problem: attackers constantly change their techniques. A new malware that nobody has seen before won't match any signature.

AI-driven security detects threats by behavior, not signatures. It learns what "normal" looks like and flags anomalies.

Use caseHow AI helpsTool
Intrusion DetectionML models trained on attack patterns detect new variantsSnort + ML, CrowdStrike
DDoS DetectionDistinguishes legitimate traffic spikes from attack floodsCloudflare, AWS Shield
Insider Threat (UEBA)Flags when an employee downloads unusual amounts of dataVaronis, Exabeam
Zero-day DetectionCatches unknown malware by behavioral analysisDarktrace, SentinelOne
Phishing DetectionNLP models analyze email text/links for phishing patternsProofpoint, Microsoft Defender

Real example: Insider threat detection

Normal user baseline (learned over 30 days):
  - Logs in from: New York, 9am–6pm
  - Downloads: ~50MB/day from internal systems
  - Accesses: HR system, project folders

Anomaly detected:
  - Login from: Moscow, 2am
  - Downloads: 50GB in 20 minutes
  - Accesses: ALL financial records

→ AI flags this, blocks the session, alerts security team

Engineer types:  "Block all inbound traffic from China except port 443"

AI generates:
  iptables -A INPUT -p tcp --dport 443 -j ACCEPT
  iptables -A INPUT -m geoip --src-cc CN -j DROP

Config drift detection

Your intended config: "All web servers should have port 22 closed". AI checks all 500 servers every hour. If server #247 has port 22 open (maybe someone opened it for debugging and forgot), AI alerts immediately or auto-closes it.

Tools: Cisco DNA Center, Juniper Apstra, AWS Config, Ansible + LLM integration

What is ChatOps?

ChatOps is running operations tasks through a chat interface (Slack, Teams) instead of logging into servers. Add an LLM (like Claude or GPT) and now your chat bot can query your infrastructure, diagnose problems, and take actions.

Example interaction

DevOps Engineer in Slack:
  "@ops-bot why is the checkout service slow?"

LLM Bot:
  Checking Datadog... Kubernetes... logs...

  Root cause found:
  - checkout-service Pod #3 is consuming 98% CPU
  - Spike started at 14:32 UTC (18 minutes ago)
  - Correlates with deploy of version 2.1.4
  - The /calculate-tax endpoint has a new N+1 query bug

  Recommendation:
  1. Roll back to 2.1.3: kubectl rollout undo deploy/checkout
  2. File bug against PR #847 (merged at 14:30 UTC)

  Shall I roll back? [Yes / No]

What you can build

  • Runbook automation — LLM reads your runbooks and follows them automatically when an alert fires
  • IaC generation — "Create a Terraform module for a 3-tier web app in AWS" → LLM generates it
  • Incident postmortems — LLM reads all alert history, logs, and deploys → writes the postmortem draft
  • On-call assistant — LLM answers "what does this alert mean and what do I do?"

How to build one (simple version)

1. Set up a Slack bot (Slack API)
2. Bot receives messages from engineers
3. Send message to Claude/GPT API with:
   - The engineer's question
   - Current metrics from Datadog API
   - Recent logs from CloudWatch API
   - Current K8s state from kubectl
4. LLM reasons over all that data
5. Bot posts the answer back in Slack
Start simple — even a bot that can answer "what is the current CPU usage of pod X?" is immediately useful and teaches you the pattern.
